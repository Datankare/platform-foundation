# ADR-058: One Bound on Every Stored JSON Value, Enforced by the Database

Status: Accepted (2026-11-17, batch 56e-3a, platform TASK-229; Playform TASK-5030); revised 2026-11-18 after two independent code reviews of the batch (their findings are cited as "code review A-n / B-n"). Decision maker: the architect, under the owner's brief for 56e-3a (2026-11-17: not live, no data to preserve, formats may change, every finding fixed). Related: ADR-053 (tenancy, `app_tenant`), ADR-056 (readiness, the deploy smoke, the health watch), ADR-057; migrations 052 (today's erasure rewrites), 074 and 075; `platform/errors/json-limits.ts`, `platform/errors/json-columns.ts`, `platform/auth/erasure-schema.ts`; `docs/JSON_BOUND.md` (the bound's one definition, with its measurements and the per-column table); `docs/PORTABILITY.md`.

---

## 1. Context

The platform stores JSON documents (an agent run's steps, a held action's payload, an audit record's details, a session's state). The erasure reads each such document, replaces the person's address or id, and reads the text back into a document. Two things were unbounded:

- **Depth.** Reading a document back is recursive, so a document deep enough failed the erasure on every retry; on arm64 each level costs about 17 % more stack than on x86-64 — measured under emulation (qemu), not on Apple hardware; what was observed on the owner's Mac is the failure itself (its gate failed `r10-erasure.db.test.ts` "depth 16 340"), and the Mac gate is the proof on arm64 (`docs/PORTABILITY.md`).
- **Printed size.** The database stores numbers compactly and prints them in full: 40 KB of `5e-324` prints 49 MB, and every erasure path reads the printed text.

And today's rewrites could lose data: the purge's `regexp_replace(<col>::text, id, 'erased', 'gi')::jsonb` kept one of two keys it made equal (review A-1) and matched an id across a JSON escape (`\u0006` + `f1c2…` reads as `…6f1c2…`: review TA-a-1); 052's soft-delete rewrite counted keys with a pattern a string beginning `": "` fooled (review A-2).

## 2. Decisions

**D1 — One bound, one measure, enforced by the database for every writer.** A stored JSON value is at most **128 levels** deep; every number in it is **0 or 1e-18 ≤ |n| < 1e21**; it prints at most **8 MiB** (8 388 608 bytes) of text — `octet_length(value::text)`, the one meaning of "size" for this batch and batches 3b and 3c (`docs/JSON_BOUND.md`). Two `BEFORE` triggers per table (`zz_json_bound_ins`, `zz_json_bound_upd`), named to fire after every other `BEFORE` trigger, `ENABLE ALWAYS` (they fire under `session_replication_role = replica` too). The whole test is in `WHEN`, built-in functions only, cheapest first; no PL/pgSQL runs unless a write is refused, and no role needs EXECUTE on anything of ours to write (review B-7). The term, as `public.json_bound_term('new.c', 8388608)` returns it on PostgreSQL 17.6:

```sql
((pg_column_size((new.c || '[]'::jsonb)) > 33619968) OR jsonb_path_exists(new.c, 'strict $.**{128}?(@.type() == "object" || @.type() == "array")'::jsonpath) OR jsonb_path_exists(new.c, 'strict $.**?(@.abs() >= 1000000000000000000000 || @.abs() < 0.000000000000000001)?(@ != 0)'::jsonpath) OR (octet_length((new.c)::text) > 8388608))
```

On UPDATE a value is "unchanged", and not read, only when it is the same stored toast pointer as before (`pg_column_toast_chunk_id` equal and not null: review B-4); a value held in line, or a new one, is always tested. (As first built an in-line value was passed when equal to the old one as jsonb — but jsonb compares numbers by value, so plain zeros could be updated to zeros written with a scale that print 16 385 characters each, with no test: code review A-1.) So an update of another column re-tests the row's in-line values (a few microseconds for a small one), and a row already holding an in-line value over the bound refuses every update until it is converted (D6). A refused write gets `23514 check_violation`, constraint `json_bound`, the column and the reason named, from `public.json_bound_refuse()` — a `SECURITY DEFINER` that only raises, so `app_tenant` is refused with 23514, never 42501 (finding NF-2). `agent_trajectories.steps` (a whole run in one document) has the depth term only until migration 076 makes the steps rows.

- **Why 128:** the application refuses deeper than 64; 128 leaves 2× for writers without that limit and is 3.0× below the shallowest failing depth of any erasure operation at `max_stack_depth = 100kB` on arm64 under qemu (`@>` at 385; x86-64, native, 419) — `docs/PORTABILITY.md`.
- **Why the number range:** inside it a number prints at most 4 × as long as `JSON.stringify` writes it, so an application-written value (≤ 1 MiB compact) prints ≤ 4 MiB; outside it a few stored bytes print up to 100 000 characters.
- **Why 8 MiB:** the lowest power of two above the most an application-written value reaches after today's soft delete. Measured on 1 MiB of compact JSON made of a 3-character address: 6.67 × as an array of it (6.99 MB), and at the worst found — the address as key and value in objects of its four case variants, the keys numbered with the document's digest — 7.95 ×, 8.33 MB of the 8.39 MB allowed (pinned by `__tests__/db/json-bound.db.test.ts`; code review A-22: "6.7 MiB after any erasure" was the array alone). 4 MiB would refuse an erasure of an app-legal value.
- **What the check can cost** (review CONFIRM CA3-1, measured). A SQL text writer (owner, scripts, secret key) can make the check print up to PostgreSQL's 1 GB limit from ~700 KB of zeros written with a scale (`0e-16383` is ~8 bytes sent and prints `0.` and 16 383 zeros: jsonb keeps a zero's display scale, and the number rule lets every zero through). Measured: 2.6 s, about 2.1 GB peak in that backend, refused with 54000 out of memory instead of 23514. An object root just under the stored-size pre-test costs ~2.5 s and ~1 GB (`|| '[]'` re-encodes it). The application cannot produce either (`JSON.stringify` writes 0; requests are schema-closed). Accepted: only holders of the secret key reach it. Whatever the cost, anything that prints more than 8 MiB is refused, on INSERT and on UPDATE — by 23514, or by 54000 for the scaled zeros. Ordinary writes pay +0.03 ms (small) to +9 ms (1 MiB of words); 1 MiB of compact zeros, the most node-dense app value, +284 ms.

**D2 — The application refuses first, coded.** `storedJsonViolation` (every checked writer) gains the number range: `request.json_number_out_of_range` (HTTP 422, params `min`, `max`). Writers with no limit of their own check too (`assertWithinDatabaseBound`). The same check refuses what JSON or jsonb cannot hold at all — a text with U+0000 or half of a surrogate pair, a BigInt — with `request.json_value_not_storable` (422; code reviews B-12, B-30: `JSON.stringify` writes such a text and the database refuses it, after the work).

_Refused before the work._ Everything of an action's step that is known before it performs — its input, its declared output, its cost and label, as one step — is tested first, and a tool with declared external effects is not run with an input its effect ledger would refuse as a request (code reviews B-2, B-3); a session's metadata is tested before anything of the session is stored (B-7).

_Never failed after the work._ Where the work a value records has already happened, nothing fails after it: what an action's `perform` returned, an agent run's step and a tool's output are recorded as `outputNotRecorded` / `inputNotRecorded` (and a cost that cannot be stored as 0 with `costNotRecorded`) — the run goes on, its budget consumed; a compensation's step likewise, and a step that cannot be stored is reported while the walk goes on; a classifier's output is stored as the marker `{"_omitted": {"code": …}}` (`classifierOutputNotKept`), and a moderation result always keeps its own fields (`fieldsNotKept` names any other that was dropped); a metric is dropped alone. Every such case is logged and counted.

_An effect's receipt_ has its own limit, 6 MiB as the database prints it (`EFFECT_RECEIPT_MAX_TEXT`; about 4.4 MiB of image data as base64): it is what an approval later delivers, and no erasure rewrites the effect ledger. As first built it shared the 1 MiB of other documents, so a held image over ~768 KB was never deliverable — approved, found "no longer available", generated again, held again, a paid generation per round (code review B-1). Over its limit a receipt is stored as the marker and replayed as `resultKept: false`; the live call says `replayable: false`, and a generation that would be held for approval is `withheld` instead, naming the largest image a held generation keeps. The marker is one of the stored-JSON refusal codes under the single key `_omitted`; a real value of that shape is stored wrapped (`{"_kept": …}`), so a provider's answer is never read as "not kept" (code review B-11).

_Computed numbers._ Ordinary arithmetic on small amounts leaves numbers under 1e-18: `(a + b) - a - b` on sub-cent amounts is non-zero and below the range in about half of all cases (code review B-6: `0.00832 + 0.001586` less both is 6.5e-19). Such a value is refused like any other number out of range. **A writer that stores a computed amount rounds it first** to the precision it means (`Math.round(x * 1e9) / 1e9`); the platform's own stored money fields are sums of provider prices, not differences, and a step's cost that is nevertheless out of range is recorded as 0 with `costNotRecorded`. Every jsonb column is in a register (`platform/errors/json-columns.ts`, an app's own in `platform/auth/app-json-columns.ts`) compared in CI with the catalogue and with the source: a file whose SQL writes a registered column must be named in its row, and a registered check must still be called (`docs/JSON_BOUND.md` §5).

**D3 — Readiness names every way the bound is not in force; only the erasure's own functions gate the erasure.** `public.json_bound_missing()` reports, by name: a trigger missing, off, edited or out of date with its table's columns; rows not read since the triggers were made or toggled, or since the table gained a partition (the mark names the catalogue versions of its triggers and of its partitions' clones — a table attached with rows brings rows nobody tested: code reviews A-5, A-21); a later `BEFORE` trigger; a rewrite rule; a column the bound cannot hold; one of the nine functions that decide a refusal or what is installed where changed (definition, owner, grants — fingerprints taken by 074; code review A-6: `json_bound_limit` answering 0 switched two tests off unseen); 074 or 075 not recorded; the gate's rows; a function `anon` or `authenticated` may run; a role of the API holding TRIGGER on a covered table (it could replace a trigger of the bound with its own; `json_bound_install` takes the privilege away, and Supabase's default grants — or an older migration applied again — give it back: code review A-7). A partition is named with its root, which is what `json_bound_install` repairs. The probe `json-bound` turns any line into health `degraded`; the deploy smoke requires it healthy, and the hourly health watch from promotion. The erasure itself (soft delete, purge, cross-tenant pass) refuses only when `public.erasure_functions_missing()` names its two rewrite functions — never because the operator switched the bound off: an emergency switch must not become a refusal of every deletion. A refused purge counts no attempt (review B-13); a dry run is never refused (B-12).

**D4 — The emergency off is per table and reported.** `json_bound_off(array[…])` disables a table's triggers (removing their cost), `json_bound_install(array[…])` puts them back, `json_bound_check('<table>')` reads its rows again. Every lock the bound takes goes through `json_bound_lock`: one budget per attempt (half of `deadlock_timeout`, at most 100 ms), giving way to the application and retrying for 30 s, then failing with the table and its holders named — so no application transaction ever waits on it past `deadlock_timeout` (review TA-a-2).

**D6 — Rows already over the bound are converted, never deleted.** Rows stored before 074, or while the bound was off, may be over it: every build before this one had no number range. `json_bound_check` (075) names every such row — the first 50 of each table and the count of the rest — and `public.json_bound_convert([table])` converts them: a number under 1e-18 in magnitude becomes 0, a number of 1e21 or more its digits as a string, and a value then still too deep or too long the "not kept" marker. It never deletes a row; one that another rule of its table refuses to change is named and left as it was. Until a row is converted every update of it is refused with 23514 `json_bound` — an erasure that must rewrite it included — so the owner's procedure counts such rows before 074 and converts them between 074 and 075 (code review A-2). The conversion's rules are the reviewer's proposal, built under the owner's "convert, never clear"; their wording has not been put to the owner.

**D5 — Today's rewrites lose nothing and match only real text.** `jsonb_erase_id_text` (the purge) sets every escape PostgreSQL prints aside before matching and puts them back; `jsonb_erase_address_text` (the soft delete) is 052's function with keys compared by the text's length and no stand-ins. Both compare the printed length before and after: equal means nothing merged; otherwise the keys holding the id or address are numbered (`erased#n`, `<id>#n`, with the document's digest if needed), and a merge that numbering cannot resolve raises (never reached in the fuzz). ASCII-only case folding in collation `C`; `standard_conforming_strings` pinned. 052's function stays for the build before this one.

## 3. Consequences

- PostgreSQL 17 is the minimum (production and CI are 17.6). Migrations that add a jsonb column call `json_bound_install` and `json_bound_check` for its table, or the replay's floor (`json_bound_missing()` empty) fails.
- **A covered jsonb column cannot have its type changed, or be dropped, while the triggers stand** (code review A-23): PostgreSQL answers "cannot alter type of a column used in a trigger definition". A migration that does either — 076 drops `agent_trajectories.steps` — does, in one transaction: `drop trigger zz_json_bound_ins on <table>; drop trigger zz_json_bound_upd on <table>;` the change; `select public.json_bound_install(array['public.<table>'::regclass]);` `select public.json_bound_check('public.<table>');` (the locks through `json_bound_lock(…, 'ACCESS EXCLUSIVE')`).
- **After a restore, a branch copy or a major-version upgrade** (code review A-14) every trigger row has a new catalogue version, so every table reads "existing rows not checked" and the deploy smoke fails until `select public.json_bound_check();` has run. A major version that prints a function's definition differently changes the fingerprints: readiness line 6 names the functions, and the erasure's gate refuses every erasure until 074's functions are made again (`docs/runbooks/jobs.md`, "After a restore or an upgrade"). Both fail safe; both are an operator's step.
- A migration older than 074 applied again (049 and 050 grant all on their tables to `service_role`) gives TRIGGER back: readiness names the table and `select public.json_bound_install();` takes it away (the replay proves exactly that after its own re-applications).
- Batches 3b and 3c size everything by printed bytes (`docs/JSON_BOUND.md` §7); 3c-1 retires the gate, the two rewrite functions, readiness line 8 and the optional address script.
- **A build older than this one on a 074 database does not run unchanged** (code reviews A-24, B-9): its writers have no number range, so a write holding a number outside it — or printing more than 8 MiB — gets the database's 23514 as an uncoded 500, for a receipt or a step after the work; its erasure still calls 052's function and is refused on a row over the bound like the new one's; and it has no `json-bound` probe, so its health shows nothing. That is dev between the paste of 074 and the push, and staging (an old build on the shared dev database) until promotion — its cron is paused until then (the owner's decision of 2026-11-17).
