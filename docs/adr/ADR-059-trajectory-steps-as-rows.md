# ADR-059: An Agent Trajectory's Steps as Rows

Status: Accepted (2026-11-17 design, built 2026-11-20 — batch 56e-3b, platform TASK-230; Playform TASK-5032; round 2 the same day, before 076 was applied anywhere: a rewrite's bookkeeping once per statement, D2). Decision maker: the architect, under the owner's brief for 56e-3b (2026-11-17: convert, clear nothing; every limit enforced by the database; not live, formats may change). The design passed two independent design reviews (B3-DESIGN-REVIEW-A / -B) and a confirmation review (CONFIRM-56e3b), whose ids are cited here. Related: ADR-029 (trajectories), ADR-053 (tenancy, `app_tenant`), ADR-058 (the JSON bound; `docs/JSON_BOUND.md`, the one measure of size); migrations 052 (the chain guard), 074/075 and 076; `platform/agents/postgres-trajectory-store.ts`, `platform/auth/user-data.ts`, `platform/auth/erasure-schema.ts`.

---

## 1. Context

An agent run (a _trajectory_, one segment of a chain) kept its steps as one JSON document, `agent_trajectories.steps` — up to 1 000 steps and 16 MiB. Every append read the whole document and wrote it back (a 1 000-step run: 31 ms for one step; 333 ms at 16 MB), every reader loaded all of it, every erasure rewrote all of it, and the limits were the application's to keep: a direct writer could append past them, out of order, or into a segment that already had a continuation (reviews SA-8, SB-10).

## 2. Decisions

**D1 — A table of steps, keyed by tenant, run and place.** `agent_trajectory_steps (tenant_id, trajectory_id, seq, step jsonb, created_at)`, primary key `(tenant_id, trajectory_id, seq)`, foreign key `(tenant_id, trajectory_id)` to `agent_trajectories (tenant_id, id)` on delete cascade — a step can never attach to another tenant's run, whoever writes. Row-level security enabled and forced (049's tenant policy). `app_tenant` may read, insert and update the `step` column only; no delete (a step goes with its run). `anon`, `authenticated` and `service_role` have nothing. `agent_trajectories` gains `step_count`, `steps_bytes` (the steps' text as printed, summed — ADR-058's one measure) and `continued`; its `steps` column is gone. A step is a stored JSON value like any other: 074's bound applies to it (128 levels, the number range, 8 MiB of text).

**D2 — The database keeps every rule of the steps.** One row trigger, `zy_agent_trajectory_steps_guard` (`ENABLE ALWAYS`, named to fire after every other `BEFORE` trigger but the bound's), checks each row before it is written; two statement triggers, `agent_trajectory_steps_appended` and `agent_trajectory_steps_rewritten` (`AFTER INSERT` / `AFTER UPDATE … FOR EACH STATEMENT` with transition tables, `ENABLE ALWAYS`), count what the statement wrote and update each run **once** (round 2, below):

| On                       | Rule                                                                                                                                                                                                                                                                                                                                                                                       | Refusal                                                                    |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| INSERT, each row         | locks the run's row and reads `continued` and the counters **from that locked row**; never into a continued segment; the step's `seq` is `step_count` — or, for a later row of a statement appending several, the place right after the row the statement put before it (never a gap, never a place taken); at most 1 000 steps                                                            | `23514` `trajectory_step_order`, `trajectory_full`, `trajectory_continued` |
| INSERT, each statement   | the statement's rows counted per run from the new transition table and each run updated once: `step_count`, `steps_bytes`, `version`; the segment stays within 16 MiB of text, or the whole statement is refused                                                                                                                                                                           | `trajectory_full`                                                          |
| UPDATE, each row         | tenant, run and place never change; a changed step takes its run `for update skip locked` — already this transaction's, or free, never waited for — before it is written                                                                                                                                                                                                                   | `trajectory_step_fixed`, `55P03 lock_not_available`                        |
| UPDATE, each statement   | the statement's change summed per run from the old and new transition tables — each row's old and new version paired by grouping both on the row's key (which never changes), not by a join — and each run updated once: `steps_bytes` and `version`; the segment stays within 128 MiB of text (16 MiB × 8, above the most an erasure grows one: 5.71×), or the whole statement is refused | `trajectory_full`                                                          |
| DELETE outside a trigger | refused while the run exists — but for a **deleted** tenant: 049's `tenant_purge` deletes a tenant's tables leaves first, the steps before their runs (confirmation CB3-1)                                                                                                                                                                                                                 | `trajectory_step_kept`                                                     |

The chain guard (052's, replaced) keeps its rules on the counters: a continuation's `step_offset` is its predecessor's `step_offset + step_count`, and the continuation **marks its predecessor `continued` in its own statement** — a new row version, so an append that waited for that row reads it (READ COMMITTED) or fails to serialize (REPEATABLE READ, SERIALIZABLE): never appended, the chain never misnumbered (review TA-b-1; the earlier form read `continued` with the snapshot taken before the wait). The counters change only inside the steps' statement triggers and `continued` only inside the chain guard.

_Round 2 (2026-11-20, before 076 was applied anywhere)._ Round 1 moved the counters and `version` in the row trigger, once per row: the erasure's rewrite of a full segment updated one run's row 1 000 times (about 145 of 185 ms; the erasure of a shared session about 5× its cost before 076), and under twelve test workers on two CPUs that pushed one erasure past the 10 s statement timeout. The counting is now the statement triggers': one update per run per statement, whatever the number of steps (`__tests__/db/trajectory-steps-counted-once.db.test.ts` counts the run's row versions written in its transaction: 1, not 1 000, for an append and for a rewrite). The 16 MiB and 128 MiB bounds are checked on the statement's final total — what is stored — instead of after each row; a refusal refuses the whole statement either way. The statement triggers join nothing: the transition tables have no statistics (under `app_tenant`'s row-level security the planner expects one row), and a join of the old and new tables planned as a nested loop compared every old step with every new one (measured: 3 s for a full segment). The same test forces every join to a nested loop and reads every plan the statement runs through `auto_explain`: no node handles steps × steps.

**D3 — 076 converts, clears nothing, and is safe pasted twice.** One `DO` statement: refuses a role that cannot see every row (first, so it is not told 074/075 are missing — confirmation C-3), and refuses without 074 and 075; pasted again with everything in force it returns before taking any lock (review TB-b-1: a re-paste while the new build appends could otherwise deadlock); otherwise takes both tables' locks through 074's `json_bound_lock` (never aborting an application transaction), creates what D1/D2 describe, converts the stored steps with one `INSERT … SELECT` over `jsonb_array_elements` (a value that was not an array becomes one row), sets the counters and `continued`, drops the column, installs and reads 074's bound **on these two tables only** (an emergency off elsewhere is left as it is: review TA-b-5), adds the steps table to the platform's deletion manifest, and creates its readiness `public.trajectory_steps_missing()`. A converted step over the bound stops 076 naming the run and its place; nothing is changed. Measured on a seeded copy: 18–29 MB of step text per second; every reader and writer of trajectories waits for the whole conversion.

`supabase/optional/076_rollback.sql` undoes it exactly — the rows back into `steps` in order, 052's chain guard back, the table (with its triggers), both trigger functions, counters, `continued` and readiness dropped — and makes due again only the purges whose last attempt failed **after** 076 was recorded, with that attempt uncounted (reviews TA-b-6, TB-b-4). Pasted twice it changes nothing; 076 can be pasted again after it.

**D4 — A reader reads one segment in one statement; a list reads no steps.** `getById`, `chainTail` and `chainSegment` select the segment and `json_agg` of its rows in seq order in one statement — no reader sees a header and steps from different moments, and at most one segment (≤ 1 000 steps, ≤ 16 MiB by appends, ≤ 128 MiB after the worst erasure) is read. `query()` returns every record with `steps: []` and `stepCount` (review 12 M2's opt-in became the rule). `addStep` appends one row and returns where it went — `AppendedStep {trajectoryId, segment, stepIndex, version}` — never the segment's steps; the action pipeline's result carries it as `appended` (confirmation CB3-2), and a caller that needs the segment reads it with `getById`. An append reads no other step (counted: 0 toast blocks).

**D5 — Every rewrite of steps locks its runs first, in key order.** The erasure's statements on steps (the soft delete's address rewrite; the purge's `heldAboutStepNotes`, `stepFreeText`, `sessionMoveText`, `trajectorySteps`) take one form, `stepUpdateLockingTrajectories(where, set)` (`platform/auth/user-data.ts`): the runs holding a step to rewrite found once and locked in `(tenant_id, id)` order, then the steps rewritten — the update reads the condition itself, with the same snapshot, so it rewrites exactly the steps found, each checked again on its current row. Round 2: no step is joined back to the steps found (round 1's form rejoined them; without statistics the planner ran that join as a nested loop, 1 000 × 1 000 rows for a full segment's erasure, 2.5 s). Since the step trigger never waits for a run (D2), two such statements on one run serialise at the run and never deadlock (review TA-b-3); a writer that did not lock first meets 55P03 at once. The run's scope (`trajectoryScopes`) is its own statement on `agent_trajectories`. The address rewrite numbers colliding keys within the value it is given — each step now, the whole run before — so a key's `#n` suffix may differ from the document form; the members, their values and what is erased do not (review TA-b-4, `__tests__/db/erasure-steps.db.test.ts`).

**D6 — Every delete that takes runs is bounded by their steps.** A run's steps go with it by the foreign key's cascade, so retention's `deleteFinishedBefore`, `deleteOrphanedSessionRuns` and the `app_sessions` rule (its delete trigger takes the sessions' runs) delete the due rows oldest first while their `step_count` adds up to at most `TRAJECTORY_RETENTION_STEPS` (50 000; the first always), and report `more` whenever a due row was left by either bound (confirmation CB3-4: `deleted >= batch` said "done" when the step bound stopped a batch). The reaper ends every abandoned run, then — in the same transaction — gives each one the closing step only where it fits (fewer than 1 000 steps, 16 MiB with the step's printed text); a full run is ended without it, as before (confirmation CB3-3: one full run otherwise failed the reaper's whole batch on every tick).

## 3. Consequences

- **Storage.** Rows compress one by one: 1.55× the document storage on the design's seeded data, 1.8–4.2× on the reviewers'. Accepted for O(step) appends, bounded reads, database-kept limits and erasure units. The dropped column's data stays in `agent_trajectories` until its rows are rewritten or `VACUUM FULL public.agent_trajectories;` runs — nothing here is live, so the procedure does nothing about it; an adopter with data may run that one statement.
- **The window.** From 076 until the new build is deployed, the build before it cannot create, read or append to a run (every statement naming `steps` fails); its soft delete fails whole and its purge backs off. 076 is pasted only with the release ready; if the push slips past the hour, the rollback is the action (`docs/MIGRATION_v5_to_v6.md`). A new build on a database without 076 refuses every erasure up front (its gate reads `trajectory_steps_missing()` lines 1–3) and readiness `json-bound` reports 076 missing.
- **074's `json_bound_limit` is left as 074 made it.** Its one exception (`agent_trajectories.steps`, depth only) names a column that no longer exists, so every remaining column gets the whole bound; replacing the function would make 074's readiness name it (it is fingerprinted: ADR-058 D3), and the rollback needs the exception again. (The design had 076 replace it; built otherwise, with this reason.)
- **What batch 3c keeps.** Every statement that updates `agent_trajectory_steps` locks the runs it touches first, in key order (D5), or meets 55P03. A step is ≤ 8 MiB of printed text; a segment ≤ 16 MiB by appends, ≤ 128 MiB in the worst case. **`app_tenant` keeps UPDATE on the `step` column**, bounded by the step trigger (128 MiB per segment): today's soft delete and purge run as `app_tenant` and rewrite steps. Whether that right is revoked when 3c-1's sweep (as the owner) replaces those statements is **3c-1's decision** — recorded in its design's interface notes (review S-1). 3c-1 retires `stepUpdateLockingTrajectories`, the five step statements, `erasure-steps.db.test.ts` and the gate's `trajectory_steps_missing()` lines; the table, its triggers, `continued`, the readers, retention, the rollback and the readiness stay.
