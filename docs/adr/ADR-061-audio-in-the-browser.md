# ADR-061: Audio in the Browser — One Strictly Checked WAV

Status: Part 1 Accepted (2026-11-17, batch 56f-1, TASK-234; §5 added 2026-11-18 from the first run on the owner's Mac, §6 from the second). Decision maker: Raman Sud — the decisions marked **Owner's decision** were his, on the dates given. Parts 2 and 3 are appended by the batches that build them.
Related: ADR-054 (the audio-convert module), ADR-055 (deploy anywhere); `docs/AUDIO_CONVERSION.md` (the adopter's guide); `platform/voice/canonical-wav.ts`, `platform/voice/browser-audio.ts`, `platform/voice/browser-recorder.ts`; `e2e/audio/` and `.github/workflows/browser-audio.yml` (platform-foundation's cross-browser gate).

## Part 1 — the browser module, the strict check, the test audio and the cross-browser gate (2026-11-17)

### 1. Context

Music mode records 10–15 seconds from the microphone and asks a song-identification service which song it is; "Upload a file" sends a voice memo to speech-to-text. Both services need plain audio. Browsers record compressed audio (WebM/Opus in Chrome, Edge, Firefox and Safari 18.4+; MP4/AAC in older Safari), and a person may upload an iPhone voice memo (`.m4a`, AAC) or an MP3. The hosted converter the platform used was lost with an old cloud account.

**Owner's decision (2026-11-17 18:02):** the browser turns audio into one plain format, and the server only checks that format strictly. No server parses compressed, possibly hostile media; nothing is hosted. Only the owner's own web app sends audio. The interface stays one documented abstraction so an adopter can plug in their own service (Parts 2 and 3).

### 2. Decisions

**D1 — One canonical format.** 16 000 samples a second, one channel, 16-bit PCM, in a WAV with exactly the 44-byte header and no other chunk: `RIFF` · size = length − 8 · `WAVE` · `fmt ` · 16 · format 1 · 1 channel · 16 000 · 32 000 · 2 · 16 · `data` · size = length − 44 · even. The check compares the 44 header bytes with the header computed for the input's length, byte for byte: that one comparison covers every field, both sizes and "no other chunk" (no RF64, no extensible format, no `LIST`, no lies about sizes).

**D2 — `CanonicalWav` is a class, so the guarantee holds at run time.** Only two functions make one: `checkCanonicalWav` (server) and `encodeCanonicalPcm` (browser; a guard lets only `browser-audio.ts` import it). The constructor needs a module-private symbol; the bytes live in an ES-private field and leave only as copies; the object, the class and its prototype are frozen. A provider calls `requireCanonicalWav` at its boundary: a JSON body, raw bytes cast to the type, `Object.create`, `setPrototypeOf`, a `Proxy`, `structuredClone`, a subclass or a guessed `Symbol.for` all throw `TypeError` there. Two forms produce genuine objects and no run-time check can tell them apart — a route calling `checkCanonicalWav` itself, and silence sent to a paid provider — so Part 2 closes them with import guards.

**D3 — Limits fail closed and loudly.** A check's limits must be finite numbers (`maxBytes` an integer in (44, 4 MiB], `0 < minSeconds ≤ maxSeconds`); anything else throws `AudioLimitsError` (`misconfigured`), never passes. (Before this design a `NaN` maximum accepted a 200-second file.) The converter's own options are checked the same way.

**D4 — An upload's declared length is checked before it is decoded.** First the file's container is named from its first 16 bytes — WAV, MP3, FLAC, Ogg, WebM/Matroska or MP4/M4A, exactly the formats claimed; anything else is refused (`undecodable`) before a media element or the decoder sees it. The type a Blob declares is never used: a picked file can arrive with no type or a wrong one (drag and drop, some pickers, a renamed file), a declared type never widens what is accepted, and the media element below is given a Blob typed from the bytes (§5 says why it needs one). Then the browser reads the container's duration with `<audio preload="metadata">`; a duration-less file (a recorder's WebM reports `Infinity`) is made to seek far past its end, and the engine finds the real end without decoding the audio. A file whose length is not known within the budget (3 s) is refused (`unmeasurable`), never decoded; one longer than the limit plus 1 s is refused (`too_long`). A 1.1 MB WebM holding 30 minutes is refused with zero decode calls in every engine (as `too_long` in Chromium and Firefox; WebKit and Safari refuse that generated file as `undecodable`, also before decoding — §5, §6). **Not bounded before decoding, stated honestly** (CODE-REVIEW-A RA-1, -B RB-19): (1) a file whose container **lies** about its length — a FLAC STREAMINFO, an MP4 `mvhd`/`mdhd`, a WebM `Duration` or an MP3 Xing/VBRI count that declares less than the stream holds — passes the check on its declared length and reaches the one decode. The rule that holds in every engine: **such a file never yields more audio than the limits allow, and what an engine decodes of it is either refused or no longer than the file declared.** What the decode does is the engine's: one that reads the whole stream decodes it whole, and the file is then refused (`too_long` from the decoded length, or `out_of_memory`), but only after the decode has used memory in proportion to its real length, whose only ceiling is the 25 MiB pick limit times the codec's compression (a low-bitrate file can hold hours: gigabytes of samples); one that reads only the declared length converts that much and nothing more. `decodeAudioData` cannot be stopped part-way, so nothing tighter can be enforced without parsing the container, which this design refuses to do. The gate has a generated fixture for it (`lying-length.flac`: 575 s of silence declaring 10 s, with a limit of 60 s, so a whole decode can only end refused), and its cell says exactly what each engine does, as seen in run `b56f1r3-mac-pf-1` (§6): Chromium decodes it whole and it is refused `too_long`; Firefox's decoder refuses the file (`undecodable`, at the decode); WebKit and Safari decode exactly the declared 10 s and it converts — a cell (`bounded-by-declared-length`) that fails on any decoded or converted length beyond the declared one. (2) a file's channel count and sample rate (learning them would mean parsing the container); a 61-second file with many channels at a high rate still decodes. Both cost only the tab of the person who picked the file; a `RangeError` becomes `out_of_memory`, a killed renderer shows the browser's own page.

**D5 — A recording is trimmed to its limit, never refused for length.** A browser's recording can decode a little longer than the timer that stopped it (encoder priming, whole frames): the design's first measurement of a Safari AAC recording was 23 ms over, and Safari 26.6.2's own recordings of a 4 s timer decoded 4.0075 s (WebM/Opus) and 4.009 s (MP4/AAC) in the second Mac run. A recording is cut to `maxSeconds`. An upload may be 0.25 s over (AAC priming and padding) and is then cut; more is `too_long`. The one minimum check is on the decoded length.

**D6 — Decide by capability, never by the browser's name.** `detectAudioSupport()` asks: can a 16 kHz `OfflineAudioContext` be made; does `MediaRecorder` record one of the recorder types; is there a microphone API; can the `<audio>` element play each accepted upload format. **Owner's decision D-3 (2026-11-17, default built):** Safari older than 18.4 is **not claimed** — the recorder types are WebM/Opus then Ogg/Opus (never `audio/mp4`, the only type older Safari records, whose recordings nothing proves decodable), and uploads need all seven formats, so Safari 14.1–18.3 gets "This needs a newer browser" for the audio features only. The switch is one constant (`AUDIO_DECISIONS.claimSafariBefore18_4` in `canonical-wav.ts`) whose whole effect is `audioTypesFor()` beside it. **D-1** (Music clip 15 s) and **D-7** (largest picked file 25 MiB, separate from the server's 4 MiB cap on the converted WAV) are constants there too.

**D7 — The recorder core is shared.** `browser-recorder.ts` starts `MediaRecorder` with no timeslice (one Blob at stop; immune to WebKit bug 301507's empty Blobs), keeps the recorder's MIME type, stops once at the limit (an injectable clock, so tests use no wall clock), and turns a track ending, a recorder error or a hidden page into `recording_interrupted` — never a partial send. Part 2's hook is a thin wrapper around it, so the cross-browser gate exercises the shipped recorder.

**D8 — The work yields without timers.** Encoding works one second (16 000 samples) per slice and yields through a `MessageChannel`, which browsers do not clamp in a hidden tab as they clamp timers.

**D9 — Test audio is generated, checked and never passes through a storage that rewrites media.** Every WAV, the duration-less WebM files and the damaged input are made in code (`__tests__/fixtures/audio/generate.ts`); only files that need an encoder are committed, made by `scripts/make-audio-fixtures.mjs` with ffmpeg in bit-exact mode (the same build gives the same bytes), and the two recordings real Safari 26.6.2 made in the first Mac run (they cannot be made again, so the script carries their names, sizes and SHA-256 and writes their rows; every engine must convert them). `SHA256SUMS` lists all fourteen; `__tests__/audio-fixtures-integrity.test.ts` fails on a changed byte, an unlisted or missing file, the bytes `c2pa`/`jumb` in a media file, or audio tracked elsewhere. (A storage used while this was designed had added signed C2PA manifests to 9 of 15 audio files; decoders skip such boxes, so nothing else noticed.) The old `test-fixtures/audio/` is removed: every file carried a `LIST` chunk the check refuses, nothing read them, and one was a clip of a commercial recording.

**D10 — The gate runs in real engines, against a committed table.** `e2e/audio/expect.json` states, per engine (Chromium, Firefox, WebKit, real Safari), what each case must do; every cell is asserted, a refusal names the step of the product that refused it and must come with zero decode calls (except a file that reaches its one decode: the lying-length file, and a file within a second of the limit), and every compressed upload is converted twice — as a Blob with no type and as a picker types it — with the same cell for both. **What has been observed** (§5): the Chromium column here, in Linux CI and on macOS; the Firefox column on macOS; the WebKit and Safari columns on macOS in two runs — the second (§6) observed every cell §5 had predicted. The table's own "about" text says which cells are first tested by the next run (one new case and the new cell's assertion). platform-foundation's `browser-audio.yml` runs Chromium on Linux and Chromium, Firefox, WebKit and real Safari (`safaridriver`, a WebDriver element click as the gesture) on macOS; the owner's Mac runs the same before the first push. A macOS runner without an audio device fails as such ("audio clock not running"), never as a table mismatch. Playform runs no browser job (the modules are byte-identical); timings are logged, never asserted.

### 3. Consequences

- Nothing in the app calls these modules yet (Part 2 wires them); `__tests__/reachable-modules.test.ts` lists them as shipped ahead of their callers, and the entries fail the moment Part 2 reaches them.
- Supported browsers for the audio features: current Chrome, Edge and Firefox; Safari 18.4 or later on macOS 15.4 or later and iOS/iPadOS 18.4 or later. Firefox on a Linux without system AAC decoders cannot open `.m4a` and is told so.
- A different ffmpeg build may make different fixture bytes: the files are made again, `SHA256SUMS` changes in the same commit, a visible, reviewed change.

The last cell is where the safety would be lost silently, so it asserts the bound instead of trusting it: a conversion is accepted for this case only when the **decoded** length (before any trim) and the converted length are within 0.05 s of the declared 10 s and not over the limit, after exactly one decode with the length known from the probe first. Anything longer fails; a result with no length fails. Were WebKit to start reading the whole stream, the product would refuse the file (575 s is over every limit), the cell would fail as "refused", and the table would be changed with the run that shows it. What a person meets in Safari: a file whose header states less than it holds is converted up to the stated length — the rest is not sent. (No such file is known outside this test.)

**What a person meets with a WebM that states no length.** In Safari, a picked WebM file that has no stated length **may** be refused with the "This audio couldn't be read" message (`undecodable`): the two files this repository generates are, every time. It is not every such file — the WebM Safari's own recorder writes is measured — and which files are refused is not known beyond those two facts. Chromium and Firefox measure all of them. **Recording in the page is not affected:** a recording is never probed (`toCanonicalWav` runs the container and length steps for `source: "upload"` only; the gate fails a recording that was probed — each recording case and, from this round, each recording made in the page), and in both runs Safari recorded WebM/Opus and the shipped pipeline converted it (4 s, the tone present; the second run's result records that no probe ran).

**Corrections to what was written before this run.** "A recorder's WebM has no duration" is true of Safari's recorder (its file: a Segment and a Cluster of unknown size, no Duration) and not of every browser: the recorder of Chromium 153, examined on Linux while this was written, writes a WebM that states its duration. The gate's own two recordings differ in every run (the second run's SHA-256 values are not the first's); the committed ones are the first run's. §5 row 1's "Chromium and Firefox: about 23 ms longer" is exact for Chromium only: Firefox decoded the three fragmented-MP4 files 24 to 42 ms longer than nominal (the trim still gives the exact length).

**What the third run (`b56f1r4-mac-pf-1`) tests first.** (1) Safari's own WebM recording as an **upload** in Firefox, WebKit and Safari — a new case; its cell ("decodes") is written from the second run's separate observations of the probe and of the decoder on that file. (2) The `bounded-by-declared-length` assertion itself (its values are the second run's). (3) Reported, with no cell: how much each engine's decoder alone makes of the lying file, and what the probe answers for an 80 s duration-less WebM made in code from Safari's own recording (`nodur-80s-safari-form.webm`) — whether the seek probe in WebKit and Safari finds the real end of a long file of a real recorder's form, which the generated files could not show there. **Still open after it, and said so:** why the generated form is refused, and what Safari does with a duration-less WebM written by Firefox's recorder or by another tool. If a claimed kind of file turns out not to be convertible in Safari, it is the owner's decision as §5 says.
