# ADR-057: Server-Side Sessions — the Browser Holds No Token

Status: Accepted (2026-11-12, batch S9 of the sweep, TASK-214). Decision maker: Raman Sud — the three choices marked **Owner's decision (2026-11-12)** below were put to the owner and confirmed on that date.
Related: ADR-012 (authentication), ADR-033 (agent identity), ADR-050 (guests), ADR-051 (coded errors), ADR-052 (rate limiting), ADR-053 (tenancy), ADR-056 (jobs, readiness); `docs/SECURITY_DEBT.md` SEC-016 (closed here) and SEC-018 (what remains); register item N-30. `platform/auth/session*.ts`, `platform/auth/request-origin.ts`, `platform/auth/middleware.ts`, `proxy.ts`, migration 070.

---

## 1. Context

Until this decision a signed-in browser held the identity provider's access token in `localStorage` (`pf_access_token`) and sent it as `Authorization: Bearer` on every call; the refresh token was in an httpOnly cookie for the auth routes. Any script that ran in the page — an XSS, a malicious extension, a compromised dependency — could read the access token, take it elsewhere, and use it until it expired. Worse, a Cognito access token from a native sign-in always carries the `aws.cognito.signin.user.admin` scope, so the thief could call Cognito's own user API with it (`SetUserMFAPreference`, `ChangePassword`, `UpdateUserAttributes`, …) and go round the step-up the app's routes require (SEC-016, TASK-194 finding C1).

Two facts about Cognito constrain the answer, both checked against AWS's documentation on 2026-11-12:

- Tokens from `InitiateAuth` / `AdminInitiateAuth` always carry the single scope `aws.cognito.signin.user.admin`; scopes can be chosen only for the managed-login (OAuth) flow. (Amazon Cognito Developer Guide, "Scopes, M2M, and resource servers"; API reference, `InitiateAuth`.)
- Enrolling a TOTP factor (`AssociateSoftwareToken`, `VerifySoftwareToken`) has no IAM-signed `Admin*` form: it takes the user's access token or a challenge session. (API reference, `AssociateSoftwareToken`.)

## 2. Decisions

**D1 — The session lives on the server; the browser holds an opaque id.** (Backend-for-frontend.) Sign-in creates a row in `auth_sessions` (migration 070; tenant-owned, forced row-level security, read and written only through the data layer) and sets one cookie: `__Host-pf_session`, `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, no `Domain`. The id is 32 random bytes (256 bits); the table stores only its SHA-256, so a read of the table yields nothing a browser could present. No token is in page script's reach: not in storage, not in a script-readable cookie, not in any response body. Outside production builds the cookie is `pf_session` without `Secure` (a `__Host-` cookie cannot be set over plain `http://localhost`); a production build always uses the `__Host-` name. Without a database the store is in memory; a production process without a database refuses to start sessions (only the E2E harness, on its own host, may run so). The page learns who is signed in from `GET /api/auth/session` — once per page load, and every 30 seconds for a staff tab. That read is counted for the session its cookie names (`AUTH_SESSION_STATUS`, 120 a minute; ADR-052), not for the address: an office or a school is many signed-in people behind one address, and a per-address count would refuse some of them on an ordinary morning. A first read the server cannot answer for the moment (a limit, an error, the network) is asked again twice, briefly, before the page concludes it is signed out.

- _`SameSite=Lax`, not `Strict` (**Owner's decision, 2026-11-12**)._ RFC 10017 §6.1.3.2 and the OWASP Session Management Cheat Sheet prefer `Strict` and ask that a deviation be justified: with `Strict`, a signed-in user who follows a link from an email or another site (a verification link, a shared item, the return from an SSO provider) arrives without the cookie and is shown the sign-in page. `Lax` sends the cookie on top-level `GET` navigations only; no `GET` in the platform changes state (`__tests__/api-route-auth.test.ts` and the route fixtures), and D4 does not rest on `SameSite`.

**D2 — The provider's tokens are sealed at rest, behind one module.** `platform/auth/session-vault.ts` is the only code that seals, opens or hands out a provider token (`__tests__/session-token-confinement.test.ts`). Tokens are encrypted with AES-256-GCM before they reach the database, under a key derived (HKDF-SHA-256) from `SESSION_ENCRYPTION_KEY`; the session's id hash is bound in as associated data, so a sealed value copied to another row does not open. `SESSION_ENCRYPTION_KEY_PREVIOUS` still opens what the old key sealed, and each such session is sealed again under the current key at its next renewal: rotation signs nobody out, and the previous key is removed once the longest absolute lifetime has passed. Setting a new key without the previous one is the emergency lever — every session then fails to open and ends at its next request. A value that opens under no key ends its session (`unreadable`). The key is required wherever a real auth provider is configured.

**D3 — Renewal is the server's, and one renewal wins.** When the held access token is within 60 seconds of expiry the server exchanges the refresh token (`renewSession`) and stores the result by compare-and-set on `token_version`; concurrent requests in one process share one exchange, and across processes the loser re-reads the winner's tokens. A provider that _refuses_ the refresh token ends the session (`provider_refused`) — as RFC 10017 §6.1.2.3 asks, the session does not outlive its refresh token; a provider that _cannot answer_ is a 503, not a sign-out.

**D4 — Forgery: three defences, each for what the others do not cover.**

1. **`SameSite=Lax` + `__Host-`** — the browser does not attach the cookie to another site's `POST`, and no sibling subdomain can set or overwrite it. _Not sufficient alone:_ `SameSite` is scoped to the registrable domain, so a sibling subdomain is "same-site"; older browsers and some embedded web views apply it differently (OWASP CSRF Prevention Cheat Sheet: "useful as a defense-in-depth control but it does not replace a proper CSRF defense").
2. **Origin check** — a state-changing request (`POST`, `PUT`, `PATCH`, `DELETE`) whose `Origin` (or, absent that, `Referer`) names another origin is refused `403 auth.csrf_failed`; in `proxy.ts` for every API route (this is the defence of the routes that have no session yet: sign-in, sign-up, a guest's start — "login CSRF"), and again in the session check. _Not sufficient alone:_ a request may carry neither header, and a missing header is not evidence of the same origin.
3. **Per-session token** (synchronizer pattern) — every session has a random token, returned only by `GET /api/auth/session` (which another origin cannot read) and sent back in the `x-csrf-token` header on every state-changing request; compared in constant time. A header, not a cookie or form field: a cross-site form cannot set one, and it is not stored anywhere script-readable beyond the page's memory. _Not sufficient alone:_ it protects only requests that already have a session.

A state-changing request with a session must pass 2 (not "cross") **and** 3. The request's own origin is read from the forwarded host and scheme when present; a caller can set those headers, but a forging page cannot (a browser sends no custom header cross-site without a preflight the app never grants), so a forged request can only ever look more foreign, never less (`platform/auth/request-origin.ts`). None of this survives a script running in the page (an XSS can make same-origin requests with the token): that is what the content-security policy (SEC-001, SEC-017) is for, and RFC 10017 §5.1.4 names it as the attack a backend-for-frontend still leaves — the attacker can act through the victim's browser while the page is open, but can no longer take a credential away.

**D5 — Lifetimes are governed settings with safe bounds (Owner's decision, 2026-11-12).** Safety tier, operator-only, clamped in code as well as in the row:

| Audience                           | Idle       | Absolute | Setting                                      |
| ---------------------------------- | ---------- | -------- | -------------------------------------------- |
| Signed-in user                     | 7 days     | 30 days  | `auth.session.user_{idle,absolute}_seconds`  |
| Staff (holds any staff permission) | 30 minutes | 12 hours | `auth.session.staff_{idle,absolute}_seconds` |
| Guest                              | —          | 24 hours | `auth.session.guest_absolute_seconds`        |

Bounds: idle 15 minutes to 30 days; absolute 1 hour to 90 days. Both are enforced on the server at every request; an expired session's row is ended, not merely ignored. The audience is read from the caller's current permissions at each request (permissions that cannot be read are treated as staff — the shorter limits). The staff values follow the OWASP Session Management Cheat Sheet's ranges for low-risk and office applications; the user values are longer than it suggests, by the owner's choice for a consumer app, and an operator can shorten them to the cheat sheet's without a deploy. A staff member is warned two minutes before an idle sign-out and can stay signed in without leaving the page or losing a half-filled form (`components/auth/SessionIdleWarning.tsx`; the status poll does not itself count as use).

**D6 — A session's id changes when its authority does, and ends when its owner's standing does.** A new id on every sign-in (an id presented before sign-in is never adopted: fixation) and on a change of second factor; the old row is ended (`rotated`). Sign-out ends the row first — the record, not the provider, is what refuses the id afterwards — then revokes the refresh token at the provider (`RevokeToken`). `POST /api/auth/sign-out-everywhere` ends every session of the user and calls `AdminUserGlobalSignOut`. Every session of an account is ended when its password is reset, its role or tenant role changes, it is banned or suspended, or it is erased (`password_changed`, `role_changed`, `account_restricted`, `account_erased`). Ended rows are kept 45 days (governed, 31–400) for the record of why, then deleted by the retention job.

**D7 — The server keeps the Cognito-scoped token; the browser never sees it; everything that can be done with the IAM key is (Owner's decision, 2026-11-12 — "option A").** SSO sign-ins no longer request `aws.cognito.signin.user.admin` when the administrative key is configured. Native sign-ins cannot drop it (§1), so the token stays sealed on the server and is used for exactly one purpose — enrolling a TOTP factor (§1: `AssociateSoftwareToken`, `VerifySoftwareToken`, and the `SetUserMFAPreference` that completes the enrolment). A single sign-on session, whose token no longer has the scope, is told so (`auth.mfa_sso_managed`): Cognito applies no factor of its own to a federated sign-in. Verifying a session's user, sign-out everywhere and removing a factor use the IAM-signed `AdminGetUser`, `AdminUserGlobalSignOut` and `AdminSetUserMFAPreference`. The IAM policy grows by the last two (`docs/TENANCY_OPERATIONS.md` §3.3); until the owner adds them, sign-in keeps working, sign-out everywhere ends every session in its record and revokes each refresh token but reports `providerSignedOut: false`, removing a factor answers a coded 503, and readiness reports `sessions` not ready and names the missing action. What remains is recorded as SEC-018. The alternative of moving native sign-in to the managed-login flow, so that no token anywhere carries the scope ("option C"), is not built; because every token use is behind the vault, adopting it later changes that module and the provider, not the routes.

**D8 — A user route accepts only the cookie session (Owner's decision, 2026-11-12).** `requireAuth`, `requireActor`, `requireAdmin` and `optionalAuth` never read an `Authorization` header. A bearer credential is a machine's: after this batch exactly these read one — the jobs tick (`POST /api/internal/jobs/tick`, `CRON_SECRET`: a scheduler has no browser) and, in an app that has agents, the agent routes that take an agent's delegation token or client credential (an agent is not a browser, and its credential is issued to it, scoped and revocable — ADR-033). `proxy.ts` lets a request with a bearer through to its route without a cookie for those. The list is a register (`client-credential-register.json`, `bearerReaders`), and `__tests__/user-route-credentials.test.ts` fails when any other file reads the header.

**D9 — Signed-in users are moved, not signed out.** On its first load after the deploy the page deletes `pf_access_token`, `pf_refresh_token` and `pf_user` from storage without reading them, and calls `POST /api/auth/session/migrate` once: the legacy httpOnly refresh cookie (MAC-checked as before; same-origin only) is exchanged at the provider and becomes a server-side session. The token that was in storage is never sent or trusted. A browser whose refresh cookie is missing, forged, or refused signs in again; guests start a new guest session. `REFRESH_COOKIE_KEY` is now needed only to verify those legacy cookies and can be removed 30 days after the deploy (the refresh token's lifetime).

**D10 — It cannot quietly come back.** Guards with self-tests: no client code reads or writes a credential in `localStorage`, `sessionStorage` or `document.cookie`, and no route answers one in a body (`__tests__/no-client-tokens.test.ts`, with the register of what is allowed); no user route reads a bearer (`user-route-credentials`); no code outside the vault opens a sealed token (`session-token-confinement`).

## 3. Alternatives considered

- **Keep the token in the browser, in memory only** (no storage). Removes theft at rest, not theft by a running script, and signs the user out on every reload unless a refresh cookie re-mints it — which is this design without its benefits. RFC 10017 §8.4, §6.3.4: "not recommended for business applications".
- **Token-mediating backend** (the server holds the refresh token and hands the page a short access token). RFC 10017 §6.2: the access token is still exposed to script, and here it carries the Cognito scope. Rejected.
- **Stateless encrypted cookie holding the tokens.** No table, but no server-side revocation: a banned or erased user's cookie works until it expires, and "sign out everywhere" cannot exist. Cognito's tokens also approach the 4 KB cookie limit. Rejected for the revocation requirement.
- **Double-submit cookie instead of a per-session token.** Needs no server state, but a sibling subdomain that can set cookies defeats the naive form, and the signed form needs a secret per session anyway — the session row already holds one. Rejected.
- **Fetch-metadata (`Sec-Fetch-Site`) alone.** Good signal, not sent by every client, and the OWASP cheat sheet requires the origin-header fallback regardless; the origin check covers the same ground.
- **Sessions in the cache (Redis) instead of Postgres.** Faster reads, but the cache is optional in a deployment, is not under row-level security, and loses revocations on eviction. One indexed primary-key read per request is affordable; rejected.
- **Managed login for every sign-in ("option C").** Removes the scoped token entirely, at the cost of replacing the app's own sign-in, sign-up, challenge and recovery screens with Cognito's and re-testing every journey. Deferred by the owner (D7).

## 4. Consequences

- A script in the page can no longer take a credential away; it can still act as the user while it runs (D4). SEC-016's stated threat is closed; SEC-018 records the server-held scoped token.
- Every authenticated request reads one row (and writes it at most once a minute). Sessions can be listed, counted and ended by subject; staff sessions are short.
- New required secret wherever real auth is configured: `SESSION_ENCRYPTION_KEY`. Two more IAM actions. `REFRESH_COOKIE_KEY` becomes temporary.
- API clients that sent a user's bearer token must use the cookie session (in the repository: the E2E suites, the smoke test, the monkey and an app's live journeys, each through one helper; the k6 load scripts send no credential today — TASK-046, whose way to authenticate is now a cookie session). Agents keep their own credentials.
- Sign-out no longer fails when the provider cannot revoke: the session is ended in its record, and the refresh token expires on its own.
- The challenge handles of a sign-in in progress (`mfaSession`, `challengeSession`) still pass through the page: they are Cognito's short-lived handles for one step of one sign-in, not session credentials, and cannot be used without the password or code that step asks for.
