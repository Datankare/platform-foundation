# Migrating from v5.x to v6.x

**Released — v6.0.0, 2026-10-24 (Sprint 7R close).** v6 brings tenancy (ADR-053), the core and
product modules (ADR-054), deploy anywhere and the container image (ADR-055), background jobs and
health (ADR-056), and the October 2026 audit's Wave 2 (Sprint 7X). **Breaking** — §1 is the deploy
runbook, in the order to do it; §2 and §3 are what changes in your code and in behaviour.

Secrets in this guide are generated on your computer straight onto the clipboard and pasted
into Vercel or Supabase. They are never printed, typed into a terminal argument, committed or
pasted into a chat, an issue or a document.

---

## 1. Deploy runbook — each environment, Preview first, then Production

Do every step for the database and Vercel environment of **Preview** (staging), check it (step
7), then repeat for **Production**. Each environment gets its own secrets.

### Step 1 — Before the window: the identity provider and staff accounts

| Do                                                                                                            | Why                                                                                                                                                                                                                                                        |
| ------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| In Cognito, create a **confidential** app client (a secret cannot be added to an existing client)             | Production refuses to start with `AUTH_PROVIDER=cognito` and no `COGNITO_CLIENT_SECRET` (A-7): every call to the pool carries a `SECRET_HASH` only the server can compute, so nobody can sign up, sign in or reset a password around the platform's routes |
| Add the scope `aws.cognito.signin.user.admin` to that client's allowed OAuth scopes                           | Single sign-on asks for it, so its token can read the user record (A-13); without it SSO sign-in fails                                                                                                                                                     |
| Have every staff account enrol a second factor (`/admin` offers it)                                           | `auth.staff_mfa_required` (true, migration 052) refuses an administrative permission to a session without one (A-9). Turning it off needs a second operator                                                                                                |
| Plan a quiet period for migration 049; on a database with tables in the millions of rows, take a backup first | 049 holds its locks until it commits ([TENANCY_OPERATIONS.md](TENANCY_OPERATIONS.md) §1.1 has the size query and what to expect)                                                                                                                           |

**Release candidate (TASK-174, review 15):** `055_users_email_lookup.sql` — the same way, after 054:

```bash
pbcopy < supabase/migrations/055_users_email_lookup.sql
```

Then `select filename, confidence from public.applied_migrations where filename = '055_users_email_lookup.sql';`
lists it `verified`, and `select indexdef from pg_indexes where indexname = 'users_tenant_email_lookup_idx';`
answers `… ON public.users USING btree (tenant_id, lower(btrim(email)))`. It adds one index (an
account found by its address: the re-link at scale, the ban carry-over). **Lock:** the SQL Editor
runs it in a transaction, where `create index concurrently` is not allowed, so the build holds a
SHARE lock on `users` — reads go on, writes to `users` (a first sign-in, a profile change) wait
until it is built: 0.15 s at 100,000 accounts. On a much larger `users`, first run
`create index concurrently if not exists users_tenant_email_lookup_idx on public.users (tenant_id, (lower(btrim(email))));`
on its own (not in a transaction), then the migration, which then changes nothing but its record.
Apply it before re-linking a whole pool (§6.5 of the runbook); the code works without it, slowly.

Every one is idempotent: one already applied (046 on a database on v5.1.x) changes nothing when
run again. An app's own migrations go in between, by name (`052a_<app>_…` after 052 — §1b).

2. **Give `app_tenant` a password** — [TENANCY_OPERATIONS.md](TENANCY_OPERATIONS.md) §1.2: the

6. **An environment that applied an earlier 052** (review 8 M2, review 13 L4). 052 was edited
   before release (its function, its column and its dual-control list grew, reviews 7, 8 and 12).
   Applying this 052 again brings such an environment up to date: it seeds each dual-control key
   once and records it (`config_dual_control_seeded`), so a key an earlier copy never added is
   added, and a key an operator removed (config history shows the removal) stays off. None can exist — no environment applied 052 before v6.0.0 (PF v5.1.1
   and Playform v0.8.0 are the deployed versions; Playform v0.9.0 was never deployed) — but check.
   First the counts (review 9 M6) — erased bans by how their hash was made:

   ```sql
   select count(*) filter (where email_hash is not null) as hashed,
          count(*) filter (where email_hash_scheme = 'hmac-of-sha256') as current_form,
          count(*) filter (where email_hash is not null and email_hash_scheme is null) as unidentified,
          count(*) filter (where email_hash_scheme in ('sha256', 'hmac')) as earlier_forms
     from public.user_deletions;
   ```

   Expect `unidentified` and `earlier_forms` 0 (`hashed` = `current_form`). A non-zero
   `unidentified` means a pre-release build wrote those rows: 052 does not guess their form (a
   guess "upgraded" a review 7 row into a hash that matches nothing, and its ban was lost). Leave
   them — each still carries its ban, matched by every form when the address signs up again, and
   is rehashed then. Mark them only if you know which build wrote them, as the database owner:
   `update public.user_deletions set email_hash_scheme = 'sha256' where email_hash is not null and
email_hash_scheme is null` for the Wave 2 build's unkeyed SHA-256 (the retention job then
   upgrades them), `'hmac'` for the review 7 build's. Then the rest:

   ```sql
   select (select count(*) from public.applied_migrations where filename = '052_audit_wave2.sql') as applied,
          to_regprocedure('public.jsonb_replace_text_value(jsonb, text, text)') is not null as has_function,
          exists (select 1 from information_schema.columns where table_schema = 'public'
                   and table_name = 'user_deletions' and column_name = 'email_hash_key') as has_key_column,
          exists (select 1 from information_schema.columns where table_schema = 'public'
                   and table_name = 'user_deletions' and column_name = 'email_hash_scheme') as has_scheme_column,
          (select coalesce(jsonb_agg(k), '[]'::jsonb) from unnest(array[
     'auth.token_cache_seconds', 'auth.token_stale_grace_seconds',
     'agent.capability_features', 'agent.trusted_agents',
     'agent.delegation.max_ttl_seconds', 'agent.budget.tenant_max_cost_per_day',
     'agent.trajectory_max_segments',
     'account_status.known_features', 'account_status.restricted_features',
     'account_status.suspended_features', 'coppa.enforcement_enabled', 'coppa.blocked_features',
     'profile.screened_fields',
     'moderation.level1.block_severity', 'moderation.level1.warn_severity', 'moderation.level1.escalate_below',
     'moderation.level2.block_severity', 'moderation.level2.warn_severity', 'moderation.level2.escalate_below',
     'moderation.level3.block_severity', 'moderation.level3.warn_severity', 'moderation.level3.escalate_below',
     'moderation.translation_severity_reduction', 'moderation.transcription_severity_reduction',
     'moderation.extraction_severity_reduction',
     'moderation.strike_warn_threshold', 'moderation.strike_suspend_threshold',
     'config.approval_expiry_days'
          ]) as k
           where not coalesce((select value @> to_jsonb(k) from public.platform_config
                                where key = 'config.dual_control_keys'), false)) as not_dual_controlled;
   ```

   Expect `applied` 1 (just now), `has_function`, `has_key_column` and `has_scheme_column` true,
   `not_dual_controlled` `[]`. If the function or a column is missing, or keys are listed, run 052
   again (it is idempotent: it adds the function and columns, and every key it never seeded in
   this environment). A key still listed afterwards is one an operator took off dual control
   (`select key, outcome from public.config_dual_control_seeded where outcome = 'removed_by_operator'`
   names them); put it back, if that was not intended, as a change to `config.dual_control_keys`
   in the admin console (itself always dual-controlled: two operators, recorded in its history).

7. **Accounts erased before v6.0.0** (review 8 L1). Since v6.0.0 the soft delete replaces an
   account's address with its id wherever a held action or a run names the account by it, so
   the purge finds every mention. An account soft-deleted by v5 had its address nulled without
   that, and the address is recorded nowhere, so its mentions outlive the purge. Check whether
   there are any:

   ```sql
   select tenant_id, count(*) from public.users where deleted_at is not null group by 1;
   ```

   None: skip this. Otherwise run `supabase/optional/redact_orphan_addresses.sql` as the
   database owner, in two parts: step 1 (`-- @step list`) lists every address held as a whole
   string — a value or an object key — that is no live account's — review it, and put any address of a person whose account
   you know of but who has not signed in yet into step 2's `keep` list; then step 2
   (`-- @step redact`) replaces each listed address with `erased`, as a whole string only, in
   its own tenant. It is idempotent; step 1 lists nothing afterwards. An address inside free text
   is not reached ("What erasure does not reach", §3).

#### The shared cache — one Upstash database per environment

Boot refuses a deployment without a shared cache, and its message says what to set. For each
environment (Preview, then Production — never one database for both):

1. In the Upstash console → Redis → **Create database**: name it for the environment
   (`<project>-preview`, `<project>-production`), choose the region nearest the Vercel project's
   functions region, leave TLS on (the default). An existing database for another purpose is not
   reused: `clear()` empties its namespace, and keys would mix.
2. Open the database → **REST API** section. Use its copy button for `UPSTASH_REDIS_REST_URL`
   and paste it into Vercel → Project → Settings → Environment Variables, for that environment
   only. Do the same for `UPSTASH_REDIS_REST_TOKEN`, marked **Sensitive**. Neither is shown,
   typed into a terminal, committed or pasted anywhere else; the read-only token is not the one.
3. Set `CACHE_PROVIDER=upstash` for the environment, redeploy, and check `/api/health/ready`
   (step 7): the cache check is `ok`.

A container host (ECS, Kubernetes) sets the same two values in its secret store — or, with a
Valkey or Redis server of its own, `CACHE_PROVIDER=valkey` and `VALKEY_URL=rediss://…` there
instead ([DEPLOY_CONTAINER.md](DEPLOY_CONTAINER.md) §3, "The shared cache").

### Step 4 — Configure at boot (in your code, before deploying)

If you generate or accept images or audio: configure your classifiers (`setModalityClassifiers`)
and synthetic-media detector (`setSyntheticDetector`) at boot. Until you do, every image and audio
item is withheld and every reference image counts as synthetic (X-18).

Promote the v6.0.0 build to the environment (Preview: the `staging` branch; Production: `main`).

in Vercel and redeploy — never by turning a check off.

attribute proves "native" only if the app client can read `identities`; so, as the platform's own
provider does (`identityProvidersFrom`), treat a user as native only when the attribute is absent
**and** its pool username is its `sub` (a pool that signs in by address) **and** the app client
may read `identities` (review 17 L2 — check it once, `ENV_REFERENCE.md` "Cognito pool shape"), and
otherwise leave `identityProviders` out (unknown: nothing the token says marks an address
verified). Refuse a GetUser answer without a `sub`, or with another user's, before reading anything
from it (review 17 L1). In a
provider's GetUser handling (Playform's `askCognito` in `platform/auth/cognito-auth.ts`), beside
the other attributes:

```ts
import { identityProvidersOf } from "@/platform/auth/identity-directory";

const attr = (name: string) => attrs.find((a) => a.Name === name)?.Value;
// Review 17 L1: the answer is the token's own user's, or it is not believed.
if (!attr("sub") || attr("sub") !== subject) return { kind: "invalid" };
const identities = attr("identities");
const identityProviders = identities
  ? identityProvidersOf(identities)
  : identitiesReadable !== false && user.Username === attr("sub") // review 17 L2
    ? []
    : undefined;
return {
  kind: "valid",
  payload: {
    sub: subject,
    email: attr("email") ?? "",
    emailVerified: attr("email_verified") === "true",
    ...(identityProviders ? { identityProviders } : {}),
  },
};
```

`subject` is the token's own `sub` claim (TASK-177), never `user.Username`; `identitiesReadable`
is what your provider learnt of the app client's readable attributes (`false` once it knows
`identities` is hidden; the platform's `checkPoolShape` learns it at readiness); keep `iat`, `exp`,
`sessionId`, `tenantId` and `mfaEnabled` as before. Only a provider listed in
`AUTH_TRUSTED_EMAIL_IDPS` (default `Google`) then has its `email_verified` believed. Check it took
effect: sign in once with Google and once with a password-confirmed account, then run the SQL of
TENANCY_OPERATIONS §6.6 for each address — `email_verified` is `true` for both.

### What erasure does not reach

The soft delete replaces an erased account's address wherever a whole JSON string equals it —
as a value or as an object key, at any depth — in held actions, runs, audit details, review
cases and session state, so the purge then finds every mention by the account's id. An address
written **inside free text** — a note, a message, a moderator's comment quoting it — is not found
or replaced, in the erasure or in the export: free text is another person's writing (rewriting it
would change what they wrote), and finding an address in prose means guessing — a near miss
(`joann@` for `ann@`) is another person. Delete such a record itself when a request requires it.
