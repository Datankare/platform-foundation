# Migrating from v5.x to v6.x

**In progress — Sprint 7R.** v6.0.0 ships at the Sprint 7R close (tenancy groundwork, the
core/module boundary, background jobs, a container). This guide grows with each milestone on
`develop`; what is listed here is already there.

---

## 1. Before you deploy — every deploying consumer

| Do                                                                                                                     | Why                                                                                                                                                                                                                                                                                                                                                                                                          |
| ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Apply migrations **047–049** to every database (SQL Editor, in order)                                                  | 047 records `007_seed_separation.sql` as "absent" where its `registered` role does not exist — no role or permission changes (TASK-148); 048 creates `ai_metrics` for the metrics sink, server-only (TASK-113); 049 is tenancy (ADR-053): tenants, `tenant_id` and forced row-level security on every tenant-owned table, the `app_tenant` role, layered configuration, and the public key closed (TASK-114) |
| Give `app_tenant` a password and set `DATABASE_URL`, `DATABASE_OWNER_URL`, `DATABASE_SSL`(`_CA`)                       | Every store now reaches Postgres directly as `app_tenant`, which cannot bypass row-level security; operator paths use the owner connection. Steps: [TENANCY_OPERATIONS.md](TENANCY_OPERATIONS.md) §1                                                                                                                                                                                                         |
| Set `TENANCY_MODE=single` and `TENANT_ID=00000000-0000-4000-8000-000000000001`                                         | Production refuses to start without a declared tenancy. Existing data belongs to that default tenant. A shared deployment: [TENANCY_OPERATIONS.md](TENANCY_OPERATIONS.md) §3                                                                                                                                                                                                                                 |
| Set `CACHE_PROVIDER` in every deployed environment: `upstash` (with `UPSTASH_REDIS_REST_URL` and `_TOKEN`) or `memory` | Production refuses to start without it (TASK-139). The cache is chosen, never inferred: a Redis URL alone no longer selects Redis, and `upstash` without its credentials refuses to start instead of becoming a per-instance cache. `memory` is accepted when declared — the cache holds nothing authoritative                                                                                               |
| If you keep migrations of your own that a platform migration's effect never reached, record them truthfully            | The migration-parity check compares files with `applied_migrations` and lists "absent" records separately; a record must say what is true of the database (learning 120)                                                                                                                                                                                                                                     |

Full reference: [ENV_REFERENCE.md](ENV_REFERENCE.md).

## 3. Behaviour changes

| Change                                                                                                                                                                                                              | Who is affected                                                                                                                                                       |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Agent budget periods are UTC dates (TASK-144)                                                                                                                                                                       | Deployments on a host whose time zone is not UTC: the daily cap resets at 00:00 UTC; the first day after deploying may reset early                                    |
| `calculateAge` / `evaluateAge` live in `platform/auth/age.ts` (still exported from `coppa.ts`), take an optional `now`, never overstate age and throw `RangeError` on an impossible or future date                  | Code that passed timestamps or unchecked strings: pass a `YYYY-MM-DD` calendar date and handle the error; `recordAgeVerification` returns `{ success: false }` for it |
| `scripts/schema-parity.mjs` is replaced by `__tests__/db/sql-schema-parity.db.test.ts` (`npm run schema:check`, needs the test database): every SQL statement in the sources is planned against the migrated schema | Your own stores: write SQL as constant literals (values as `$n` parameters); a statement naming a missing table, column, conflict target or type fails CI             |
| `signups_enabled=false` now refuses sign-up (`auth.signups_closed`); it was declared but not enforced                                                                                                               | Deployments that set it to false and still expected sign-ups                                                                                                          |
| A review-queue claim, release or resolution applies only while the item is in the state it was read in (`moderation.item_state_conflict` otherwise); a release clears the claim                                     | Two reviewers acting on one item: one wins, the other is told                                                                                                         |
| The AI response cache key is SHA-256 over the request, per tenant (it was a 32-bit hash)                                                                                                                            | Cached AI responses start cold after the upgrade                                                                                                                      |
| A soft deletion is recorded in `user_deletions` and succeeds (it always reported failure: its record table did not exist)                                                                                           | Callers of `softDeleteUser`                                                                                                                                           |
| `DELETE /api/admin/config?key=…` (a tenant's own value removed) is governed like `PUT`: tier permission, two-person approval (an approval's `action` is `reset`) and dual-control holds                             | Callers that expected an immediate reset of a safety-tier or dual-controlled key: expect `202` and an approval                                                        |
| An approved dual-control hold of a config change is applied when it is approved (it was recorded as approved and never applied); under two-person approval it then waits for that approval                          | Admins approving held config changes: the change now takes effect (or moves to the second approval)                                                                   |
| One open two-person approval per key **and scope** (a change to a tenant's value and one to the platform default may both be open)                                                                                  | None                                                                                                                                                                  |
| Errors from the database are logged, not returned: a failed config or command-bar write says the change could not be saved (a taken name says so)                                                                   | Clients that parsed database messages                                                                                                                                 |
| Each tenant's agents together are capped at `agent.budget.tenant_max_cost_per_day` (default 100 USD)                                                                                                                | Deployments whose agents spend more than that a day: raise it                                                                                                         |
| Guest tokens must name their tenant (version 2); version-1 guest tokens (from before tenancy) are refused — one could have been minted by any deployment sharing `GUEST_TOKEN_SECRET`                               | Every guest: existing guest sessions end at the upgrade; the next visit starts a new guest session                                                                    |
| `isFeatureAvailable` / `requireFeature` answer "not available" (`feature.not_configured`) for a feature no registered module declares (an unknown id used to throw)                                                 | Apps that do not register a module whose feature they guard                                                                                                           |
| `GET /api/features` lists the core's features first (same keys and values)                                                                                                                                          | Clients that relied on key order                                                                                                                                      |
| The environment contract's `DATABASE_URL is required (…)` message lists the modules' durable selectors after the core's                                                                                             | Checks that matched the exact message                                                                                                                                 |
| A module slot selection outside the slot's declared values is logged at boot (and still passed to the slot, as before)                                                                                              | Deployments with a misspelt selector see a warning                                                                                                                    |
| A fresh migration replay applies the core's migrations, then the modules' (`REPLAY_MODULES`, default all); new module migrations are `NNN_<module>_<name>.sql`                                                      | Your own module migrations: name and list them in your module's manifest entry                                                                                        |
