# The bound on every stored JSON value — its one definition

Platform TASK-229, ADR-058, migrations 074 and 075 (decided 2026-11-17; revised 2026-11-18 after the code reviews of batch 56e-3a — the revisions are marked "code review"). It applies to this batch (migration 074, the application's writers) and to the two that follow it (076: step rows and segment limits; the erasure sweep's chunks, units and capacity). One definition, measured the same way everywhere. This file is the definition: ADR-058 records the decision and points here. Measurements: PostgreSQL **17.6**, x86-64, 2 shared vCPUs; median of 5, trigger on against off on the same value (the measuring scripts were the design's prototypes and are not in the repository; each figure a test pins is said so).

## 1. The decision

|                                       | Value                                                                                                                                                                                                                                                                                                                            |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Size** =                            | the **printed text**: `octet_length(<value>::text)` — the bytes PostgreSQL's `jsonb` output writes (what every erasure path reads). Nothing else is called "size" in 3a/3b/3c.                                                                                                                                                   |
| **T — the bound on one stored value** | **8 MiB = 8 388 608 bytes** of printed text, every jsonb column of every `public` table, on INSERT and on UPDATE. On UPDATE every value is tested except one that is still the same stored toast pointer as before (code review A-1: jsonb equality is not "unchanged" — `0` equals `0e-16383`, which prints 16 385 characters). |
| **Numbers**                           | a number is **0 or 1e-18 ≤ \|n\| < 1e21**; any other number is refused. (Makes printed text ≤ 4 × the compact JSON the app sends — §3 — and bounds what a check prints.)                                                                                                                                                         |
| **Depth**                             | **128** levels (unchanged).                                                                                                                                                                                                                                                                                                      |
| **P — stored-size pre-test**          | `pg_column_size` of the value as written > **4·T + 64 KiB = 33 619 968** → refused without printing. Exact: measured binary ≤ 4 × printed + 32 for every shape, so any value over P prints > T.                                                                                                                                  |
| **Transitional exception**            | `agent_trajectories.steps` (one document per run, app limit 16 MiB compact) keeps **depth 128 only** in 074; **076 drops the column** and every step row gets the full rule (§5).                                                                                                                                                |
| **App limits (unchanged numbers)**    | 1 MiB of compact JSON per document (`STORED_JSON_MAX_BYTES`), depth 64; trajectory 1 000 steps / 16 MiB per segment. **New:** the number range above, in the same check every writer already calls (`storedJsonViolation`).                                                                                                      |

Why 8 MiB and not lower: the bound must hold for the **erasure's own rewrites** (an UPDATE is tested like any write, and an erasure must never be refused for an app-written value). Today's soft delete turns an address into the 36-character account id. Measured on 1 MiB of compact JSON made of a 3-character address `a@b` (shorter than any address that passes sign-up): an array of it grows **6.67×** (6.99 MB); objects of its four case variants as keys, numbered with the document's digest because one planted key collides, **7.36×** (7.72 MB); the same objects with the address as each value too, **7.95×** — **8.33 MB of the 8.39 MB allowed** (code review A-22: the earlier text said "6.7 MiB after any erasure", which is the array alone; `__tests__/db/json-bound.db.test.ts` pins the largest). With numbers at the range edge a document prints ≤ 4 MiB. 8 MiB is the lowest power of two above all of these, with about 50 KB to spare at the worst. 3c's single-stage rewrite (address → `erased`, keys numbered) grows the same documents ≤ **2.31×** compact: inside T too. 4 MiB would refuse a soft delete of an app-legal document; 64 MiB (the previous design) let 3c's units and the check cost 8× more for no writer.

## 2. The SQL (074 writes one such term per jsonb column, in `WHEN`; built-ins only)

```sql
-- the term json_bound_term('new.c', 8388608) returns on PostgreSQL 17.6, copied from its output (E1, CONFIRM CA3-1 (3)):
((pg_column_size((new.c || '[]'::jsonb)) > 33619968) OR jsonb_path_exists(new.c, 'strict $.**{128}?(@.type() == "object" || @.type() == "array")'::jsonpath) OR jsonb_path_exists(new.c, 'strict $.**?(@.abs() >= 1000000000000000000000 || @.abs() < 0.000000000000000001)?(@ != 0)'::jsonpath) OR (octet_length((new.c)::text) > 8388608))
-- (PostgreSQL prints the jsonpath's 1e21 and 1e-18 in full; 074's source writes them 1e21 and 1e-18.)
-- the trigger's WHEN wraps it per column: ((new.c IS NOT NULL) AND <term>)
```

UPDATE adds 074's unchanged term, per column: `((pg_column_toast_chunk_id(new.c) IS DISTINCT FROM pg_column_toast_chunk_id(old.c)) OR (pg_column_toast_chunk_id(new.c) IS NULL))` — a value is "unchanged", and not read, only when it is the same stored toast pointer as the old one. A value held in line (at most about 2 KB as stored), or a new one, is always tested: the earlier term let an in-line value through when it was equal as jsonb, and jsonb compares numbers by value, so 600 plain zeros could be updated to 600 × `0e-16383` (9.8 MB printed) with no test (code review A-1; the test and its mutant are in `__tests__/db/json-bound.db.test.ts`). Two consequences: an update of another column re-tests the row's in-line values (measured once, best of 5: +2 µs per row for a five-member object, +45 µs for 40 small objects with numbers), and a row that already holds an in-line value over the bound refuses every update of the row until it is converted (§9). The `OR` is evaluated left to right and stops at the first true term (an `ExecQual` boolean step), so the print runs only for a value whose stored size, depth and numbers have passed. `pg_column_size(new.c || '[]')` is the value's size decompressed: an array root comes back unchanged (no copy); an object root is re-encoded member by member (CONFIRM CA3-1: an object just under P costs ~2.5 s and ~1 GB, §4). The source of the numbers is `public.json_bound_limit(rel, col)` (T, or 0 = depth only for `agent_trajectories.steps` until 076), `public.json_bound_depth_path()` and `public.json_bound_number_path()`; `public.json_bound_term(v, lim)` writes the text above.

## 3. Ratios after the rule (measured)

| Ratio                                                         | Worst                                                                                                                                                                                                                                                                                    | Shape                                                      |
| ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| printed / compact JSON the app sends (numbers in range)       | **≤ 4** (+2 bytes for a lone scalar)                                                                                                                                                                                                                                                     | an array of `1e-18`; separators add 1 per element (≤ 1.5×) |
| printed / binary (in memory), numbers written without a scale | ~6.0 measured (not a property: see the next row)                                                                                                                                                                                                                                         | strings of control characters (`\u0001`: 1 byte → 6)       |
| zero written with a scale (`0e-N`, `0.000…`)                  | printed / binary up to ~16 000; printed / sent up to ~2 000 — **not bounded by the rule** (the rule lets every zero through; jsonb keeps the zero's display scale, so `0e-16383` is ~8 bytes sent and prints `0.` and 16 383 zeros); only SQL text writers can store one (CONFIRM CA3-1) | `[0e-16383, …]`                                            |
| binary / printed                                              | **≤ 4.0** (+32 bytes)                                                                                                                                                                                                                                                                    | `[0,0,…]`, `[[0],…]` — this fixes P                        |
| printed / stored (compressed)                                 | **~81** measured (pglz, repetitive text at T) — not bounded by a small number                                                                                                                                                                                                            | `["aaaa…", …]`                                             |
| before the rule (for the record)                              | 1 145× stored, 20.5× binary (`5e-324`), 5 958× (`1e131071`, 22 bytes)                                                                                                                                                                                                                    | now refused                                                |

So **every stored value prints ≤ 8 MiB**; nothing may be sized by stored size (the compressed ratio is unbounded in practice).

## 4. Measured cost of the check (final WHEN; "copy" = INSERT…SELECT of a stored, compressed value)

| Value                                                                   | Check adds (in memory)              | as a copy           | Verdict                  |
| ----------------------------------------------------------------------- | ----------------------------------- | ------------------- | ------------------------ |
| `{"a":1}`                                                               | +0.03 ms (0.025 → 0.054 per insert) | +0.1 ms             | accepted                 |
| 50 KB object of text                                                    | +0.6 ms                             | +0.9 ms             | accepted                 |
| 1 MiB compact of words (app max, typical)                               | +9 ms                               | +9 ms               | accepted                 |
| 1 MiB compact of `1e-18` (prints 3.8 MB)                                | +76 ms                              | +87 ms              | accepted                 |
| **1 MiB compact of zeros** (app max, most nodes: 524 287 numbers)       | **+284 ms**                         | +288 ms             | accepted                 |
| 8 MiB printed of text (= T)                                             | +35 ms                              | +81 ms              | accepted                 |
| T + 1 byte                                                              | refused (print)                     | refused             | refused                  |
| 1 MiB compact of `5e-324`; `1e131071` (22 B); 129 deep                  | +74 ms; +0.0; +0.0                  | same                | refused before any print |
| over P                                                                  | +0.0 (pre-test)                     | +14 ms (decompress) | refused                  |
| **worst any value: zeros just under P** (2.8 M numbers)                 | **1.76 s**                          | 1.85 s              | refused                  |
| **worst print: control-character strings just under P** (prints 200 MB) | **2.2 s**, ~256 MB transient        | 2.25 s              | refused                  |

- **What the check can cost (CONFIRM CA3-1, measured).** A SQL text writer (owner, scripts, secret key) can make the check print up to PostgreSQL's 1 GB limit from ~700 KB of zeros written with a scale. Measured: 2.6 s, about 2.1 GB peak in that backend, refused with 54000 out of memory instead of 23514. An object root just under P costs ~2.5 s and ~1 GB (`|| '[]'` re-encodes it). The application cannot produce either (JSON.stringify writes 0; requests are schema-closed). Accepted: only holders of the secret key reach it. Every other in-range shape costs as the table above says (worst ≈ 2.2 s at the pre-test edge). Whatever the cost, anything that prints more than T is refused, on INSERT and on UPDATE — by 23514, or by 54000 for the scaled zeros. (Until code review A-1 that sentence was false on UPDATE for a value held in line.)
- **The cost floor is the jsonpath filter** (~0.13 µs per node for any filter, b3c); the cheapest form of the number range that is exact was chosen from five. Ordinary documents (text-heavy) pay +1–5 %; number-dense documents pay ~0.5 µs per number.
- **Copies:** a value copied from another table is decompressed once to learn its real size (`|| '[]'`), so a compressed source cannot slip past P. A copy from a table outside the bound costs at most decompressing that source (its own size), then the same tests.

## 7. What 3b and 3c must use

**3b (076, step rows):** a step row is bounded exactly as above (T = 8 MiB per step, numbers, depth) — the triggers come from `json_bound_install()`; `json_bound_limit` is left as 074 made it — its `steps` exception names the column 076 drops, so every remaining column, a step row's included, gets the whole bound (ADR-059; replacing it would make readiness line 6 name it). The **segment** counter `steps_bytes` is Σ `octet_length(step::text)` (the same measure): appends refused past **16 MiB**; **any UPDATE** that would take the segment past **128 MiB** is refused (`trajectory_full`) — 16 MiB × 8, above the most an erasure can grow a segment (5.71× printed, measured). The store's room check reads the counters (no app-side guess of the printed size). Before converting, 076 refuses (naming trajectory and position) any stored step the bound would refuse — the precheck counts them read-only.

**3c (the sweep):** size = printed text, from the statement that already prints it: the chunk statement returns `octet_length(tx.t)`; chunks are cut and units bounded by the **sum of printed bytes** (never `pg_column_size`; no "size probe" on stored size); one value is ≤ 8 MiB, one trajectory segment's steps ≤ 128 MiB in the worst case (16 MiB normally); capacity, `gdpr.erasure_capacity` and the precheck count printed bytes (per table `sum(octet_length(col::text))`). The rewrite of a value written outside the app close to T can be refused by the bound (`23514 json_bound`): 3c treats that as `row_unprocessable` (flagged, alerted), never as success. Every sweep statement that updates `agent_trajectory_steps` must lock the trajectories it touches first, in key order (56e-3b §2.5 form): 076's step trigger never waits for a trajectory on UPDATE and refuses with 55P03 when another transaction holds it. 3c's migrations take their table locks through 074's `public.json_bound_lock(tables, 'ACCESS EXCLUSIVE' | 'SHARE ROW EXCLUSIVE')` (one budget per attempt, never aborting an application transaction — TA-c-7) and, pasted again with everything in force, return before any lock (TB-c-8). 3c's address → `erased` rewrite grows an app-written value ≤ 2.31× compact (≤ 2.4 MiB): within T.

## 7a. Measured on the final 074 (interleaved, 5 rounds)

small insert 0.025 → 0.054 ms; 50 KB insert of 700 objects with numbers 1.42 → 2.54 ms (the number walk); 50 000-row bulk insert 735 → 840 ms (+14 %); change of a 1 MiB value 21.6 → 23.3 ms; update of another column beside 1 MiB / 4 MiB: no toast block read (test's own transaction counters: 0; mutant 22). Today's purge rewrite on a 12.7 MB trajectory 285 ms → 074's 514 ms (escapes set aside and put back); soft delete 363 → 410 ms.

## 8. Not verified

Supabase's instance memory (CA3-1's ~2.1 GB peak from scaled zeros, reachable only by a SQL text writer, may stop an instance with 1–2 GB of RAM); arm64 timings (the rule has no architecture-dependent part; T5 runs the depth part on the Mac); `pg_column_compression`/`|| '[]'` on lz4-compressed sources (pglz measured; the code path is the same detoast).

## 9. Rows already over the bound (code review A-2)

Rows stored before migration 074 — or while the bound was off — were written with no number range, by every build up to this one, so one may be over the bound. Until it is converted, any update of it is refused (`23514`, constraint `json_bound`): an erasure that must rewrite it fails on every retry, with the old build and the new.

| Step                                                 | What                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Before 074                                           | `0-over-bound.sql` (the migration guide's "Rows over the bound, counted"): read-only, plain SQL; per column, how many values are deeper than 128 levels, hold a number outside the range, or print more than 8 MiB. Expected: every count 0.                                                                                                                                                                                                                                   |
| 075, or `select public.json_bound_check();`          | names every such row — the first 50 of each table and the count of the rest — in one refusal                                                                                                                                                                                                                                                                                                                                                                                   |
| `select public.json_bound_convert();` (or one table) | converts them and never deletes a row or a member: a number under 1e-18 in magnitude becomes 0; a number of 1e21 or more becomes its digits as a string; a value then still too deep or too long becomes `{"_omitted": {"code": "request.json_too_deep" \| "request.json_too_large"}}`, the marker the application already reads. Each row in its own subtransaction; a row another rule of its table refuses to change is named with that rule's SQLSTATE and left as it was. |
| Then                                                 | 075 (or `json_bound_check`) again: every row within the bound                                                                                                                                                                                                                                                                                                                                                                                                                  |

The conversion's rules are the code reviewer's proposal, built as they stand under the owner's standing decision "convert, never clear" (2026-11-17); the wording of the rules themselves has not been put to the owner yet. A partition attached with rows, or a restore, makes its table "rows not checked" (the mark names the triggers' catalogue versions, the partitions' clones included: code reviews A-5, A-21), and the same three steps apply.

**What today's erasure still leaves until the later erasure batches (design 56e-3a §4.3; the owner's decision of 2026-11-17).** None is caused or widened by this batch; each is closed by the batches that replace today's erasure (step rows, then the single-stage sweep):

- an address inside a JSON-encoded string (JSON text stored as a string value) is not erased by the soft delete;
- the soft delete rewrites five tables; `jobs`, `effect_ledger`, `proposals.actor_identity` and `app_sessions.meta` are not rewritten by it;
- the pass over other tenants' audit records reads in page ranges and can skip a row that a concurrent update moves;
- the purge is one whole-table statement per register entry in one transaction: once one swept table holds about 0.5 GB of text, a purge exceeds the 10 s statement timeout and fails on every attempt — seen as `last_purge_error` and the alert `gdpr.erasure_stuck`; the migration guide's state check (`json_mb`) shows how close a database is;
- an erasure of `app_sessions.state` does not bump its version;
- revoked sessions keep their sealed tokens until the purge, and a child's `parental_consent_email` is kept until the child's account is erased;
- an address holding a quote or a backslash is matched only as a whole string.
